sibot — 技术设计

TL;DR

问题答案
sibot 是什么？一个 AI 控制中心：在一个 Web 面板里，把任务交给模型执行。
v1 做什么？配置任务，然后触发任务，然后配置 agent 执行这个任务。

0 参考项目

参考项目有七个，不是五个，也不是为了给每个轴拼一个答案。这些项目把 agent 运行时、控制中心、调度执行和自动化 UX 分别做到了很深的程度，值得完整读。sibot 的第一阶段只做其中很窄的一块：配置任务、触发任务、配置 agent 执行；其余能力不是不重要，只是排在后面。

0.2 逐个介绍

0.2.1 DeepSeek Harness（268,824）— 插件化 harness

项内容
它是什么MIT、TypeScript 的 agent harness，核心口号是 “Everything is a Plugin”，底层是 Cordis 元框架。没有特权内核：agent loop、模型适配、工具注册、会话日志、system prompt 都是可替换插件，仓库有约 255 个包。
关键机制插件树 + 能力接缝；profile / bundle / patch 三层配置层叠；append-only 会话日志；subagent 与 Agent Teams（roster、task board、mailbox）；沙箱后端覆盖 bwrap / Landlock / Seatbelt 与远程；入口有 web / SDK / ACP / headless。
值得注意的细节“模型看到的内容必须可回放”是它的硬约束；插件之间只经声明式契约交互，不互相 import；teams 的状态机（roster / board / mailbox）是现成的多 agent 原语。
我们取什么插件边界、profile / bundle / patch、append-only 日志、provider 抽象、teams 原语。
我们不取什么Cordis 绑定、255 个包的工程预算、“把竞品装进来”的单体运行时哲学。
v1 用不用不直接用。用它的边界划分来决定 sibot 的 task / run / config 怎么切。
判定架构参照第一名 —— 最完整的 harness 内部拆解。

0.2.2 OpenHands（92,478）— 平台与控制中心

项内容
它是什么自托管的 coding agent 控制中心。ACP（Agent-Client Protocol）让它能跑 OpenHands、Claude Code、Codex、Gemini、Pi、OpenCode；沙箱后端覆盖本地、Docker、VM 和云；自带 Slack / GitHub / Linear 自动化和 Web UI。
关键机制会话事件流 + 多后端沙箱；ACP 把第三方 agent 当后端接入；MCP 与内置工具并存；平台级 UI 管理会话、仓库和自动化。
值得注意的细节它把“agent 是什么”和“在哪里跑”彻底分开：同一个会话可以换后端；自动化由平台层触发，而不是写进 agent。
我们取什么平台形态、Web UX、自动化触发、沙箱隔离、按运行的历史。
我们不取什么用 ACP 聚合第三方 agent；v1 不做多后端矩阵的运营面。
v1 用不用用产品形态，不用实现。v1 不做 ACP，也不做多后端。
判定平台参照第一名 —— 证明产品形态，不证明 v1 内部实现。

0.2.3 OpenAI Agents SDK（30,449）— agent 原语

项内容
它是什么轻量 agent 框架（Python）：Agent、handoff、guardrails、sessions（SQLite）、tracing、MCP、function tools。模型以 OpenAI 为主，编排留在代码里。
关键机制agent loop + 工具调用；handoff 把控制权交给另一个 agent；agent-as-tool 把 agent 包成带 schema / timeout / budget 的工具；guardrails 做输入输出校验；tracing 记录 span 树；sessions 持久化对话。
值得注意的细节把多 agent 压缩成两个原语（handoff 与 agent-as-tool），比“图”更容易实现；guardrails 的失败语义是“立即中止”，可以映射到控制面的 policy。
我们取什么agent-as-tool、handoff、guardrails → policy、tracing 的 span 语义、session 持久化。
我们不取什么OpenAI-only、Python-only、编排写在代码里。
v1 用不用v1 没有多 agent；借它的 tracing 与 session 语义。
判定组件级参照 —— 证明少量原语足以表达 agent 循环。

0.2.4 SWE-agent（20,712）— 单任务循环与环境

项内容
它是什么单任务 coding agent：ACI（agent-computer interface）、Docker 环境、trajectory 日志、基于 SWE-bench 的评测。
关键机制ACI 把 shell 与编辑器操作收敛成模型可用的一组命令；每次任务一个 Docker 环境；完整记录 action / observation，可回放；固定数据集 + 指标做评测。
值得注意的细节环境即边界：agent 能做什么由 ACI 和环境共同决定；trajectory 是评测与调试的同一份事实源。
我们取什么代码任务循环、环境交互、trajectory 回放、eval / golden set、sandbox exec 语义。
我们不取什么单一 coding 场景、单任务模型。
v1 用不用v1 不做评测；借它的“运行记录 = 可回放事实源”和容器 exec 边界。
判定场景参照 —— 验证 loop + sandbox + eval 三件套。

0.2.5 Claude Agent SDK（8,406）— 执行内核

项内容
它是什么agent harness SDK（Python / TS）：loop、流式、工具循环、subagent、hooks、sessions、permissions、MCP。它与 Claude Code 共享同一套 loop 与权限模型，是 SKILL.md 最自然的执行环境。
关键机制内建 turn / step 循环；工具调用可被 allow / deny / ask；session 可 resume；subagent 隔离上下文；hooks 在工具调用前后插入逻辑。
值得注意的细节权限模型是执行的一部分，不是外层包装；session 与 resume 让长任务可恢复；subagent 让“父 agent 只拿结果”成为默认。
我们取什么loop、流式、工具循环、权限语义、session / resume。
我们不取什么把它当控制中心，或当唯一运行时。
v1 用不用高。它是一次运行的执行内核候选；绑定与打包方式仍未定。
判定执行内核 —— 不 fork、不重写 loop。

0.2.6 Windmill（18,357）— 调度与隔离执行

项内容
它是什么自托管的脚本与流程开发平台：cron / webhook / UI 触发，每次运行在独立 worker 里（Linux 上用 nsjail 隔离），带 Web UI、workspace、RBAC 和审计；原生支持 TS / Python / Go / Bash / SQL。
关键机制调度器 + 队列 + worker；每次执行有独立进程、沙箱和资源上限；job 历史保留输入输出与日志，可重跑；workspace 把脚本、资源、变量放在一起。
值得注意的细节“调度”和“执行”是两套组件，worker 可水平扩展；运行历史是一等页面，不是日志附件；重跑是一等操作。
我们取什么cron 调度、每次运行隔离、运行历史、重跑。
我们不取什么脚本工作流 DAG、多语言运行时矩阵、RBAC 复杂度。
v1 用不用高。v1 的“cron + 每次运行一个容器”直接照这个形状做。
判定执行与隔离参照第一名。

0.2.7 n8n（209,329）— 触发与任务 UX

项内容
它是什么fair-code 自动化工具：节点式工作流、400+ 集成、webhook / 定时 / 手动触发、执行历史、可自托管，支持 queue mode。
关键机制触发器 → 节点链；每次执行记录输入输出；工作流可启停、手动运行、重跑；节点生态负责连接外部系统。
值得注意的细节“启用 / 停用 / 立即运行”三个动作覆盖了大部分日常操作；执行历史直接回答“这次为什么失败”。
我们取什么触发 / 启停 / 手动运行的 UX、执行历史。
我们不取什么节点与集成生态、可视化 DAG 编辑器。
v1 用不用中。只借任务管理 UX，不借执行模型。
判定任务管理 UX 参照 —— 不是执行或架构参照。

1 什么是 Agent Harness

1.1 定义

Agent harness 是把模型变成 agent 的运行时。模型本身只做输入到输出；harness 决定模型看到什么上下文、能调用什么工具、会话如何持久、副作用如何受限、循环何时停止。它不生产智能，它组织智能。

harness = loop(model, tools, session, sandbox) + policy + observability
组成含义
loopturn / step / tool call 的循环
model模型通道，可替换
tools工具注册与调用
session对话与事件的事实源
sandbox文件、进程、网络的边界
policy权限、预算、审批
observabilitytrace、usage、日志

1.2 四个近义词的边界

词它是什么sibot 的取舍
Harness执行 agent 循环的运行时：loop + context + tools + session + sandbox我们不做；用外部 harness
Framework供你组合的抽象库：graph、chain、agent 类我们不做通用编排库
Platformharness + 控制平面 + 入口 + 运营sibot 是这个形态
Runtime进程 / 宿主环境（Node、容器、VM）我们只依赖，不重造

1.3 一个 harness 必须自己拥有的五件事

职责具体内容不拥有的后果
循环turn / step / tool call 的生命周期模型只能一次性问答，无法完成多步任务
上下文system prompt、history、tool schema 的组装行为不可复现，无法调试
会话append-only 事实源，可 resume / fork崩溃即丢失，无法恢复
沙箱文件、进程、网络边界，资源上限工具即任意代码执行，无法运营
治理预算、并发、审批、审计成本与风险不可控，不能上生产

这五件事在 harness 内；模型、工具、知识、入口在 harness 外，通过窄接口接入。

1.4 参考实现怎么定义 harness

参考Stars它的 harness 核心我们取什么 / 不取什么

1.5 我们做什么 / 不做什么

做不做
控制中心：任务、调度、认证、运行历史不做 harness：loop、工具执行、session 语义
多 agent / 多模型不自研模型
把每次运行交给外部 harness不做 agent 框架或编排库
运行隔离与运行记录不做通用 DAG 工作流
单用户、Web UI不做多租户平台

1.5.1 模型可替换

Model = provider + model。模型是 agent 的配置项，不是写死在任务里；换模型不需要改任务。多个 agent 可以用不同模型，这就是“多模型”。

v1 的 harness 默认是 Claude Agent SDK，它只认 ANTHROPIC_BASE_URL / ANTHROPIC_API_KEY。只要 provider 兼容 Anthropic Messages 协议，或经网关做协议翻译，就能接入——GLM、DeepSeek、Kimi 等国产模型已经提供兼容端点。

协议兼容不等于能力等价：tool use、streaming、cache、thinking、skill 行为都可能打折。每接一个 provider 都要单独做兼容性验证。

1.5.2 工具四分法

类型是什么谁提供sibot 配不配
Nativeharness 内置工具：读文件、跑命令、搜索等harness不配，随 harness 来
MCP外部 MCP server 提供的工具外部 server配（server / 连接）
Skill外部 SKILL.md 目录，一段可复用的流程或知识外部目录配（目录）
Agent另一个 agent，作为工具被调用（agent-as-tool / subagent）sibot 里的 agent配（引用）

skill 严格说不是“工具”，而是一段流程 / 知识；harness 通过一个 Skill 工具把它暴露出来。

1.5.3 agent 的定义

Agent = harness + model + tools(native / MCP / skill / agent)

sibot 配 model 和 MCP / skill / agent 三类外部能力；native 工具和 loop 由 harness 负责。

所以：sibot 是 harness 之上的控制中心。harness 执行智能，sibot 组织智能。 
sibot   = control plane(任务 / 调度 / 认证 / 运行历史 / 多 agent / 多模型)
harness = 外部依赖(loop + policy + observability)

2 几层架构

2.1 五层

flowchart TB L1["1 Entry — Web UI / REST / Auth / SSE"] L2["2 Control — 任务 / cron / 触发 / run 状态机"] L3["3 Execution — worker / 容器 / harness adapter / model / tool 注入"] L4["4 Config — agent / model / tool / policy"] L5["5 Control Plane — trace / usage / audit / eval"] L1 --> L2 L2 --> L3 L3 --> L4 L2 --> L5 L3 --> L5

Execution 里的 harness adapter 是边界：上下文组装与工具循环由外部 harness 实现，sibot 只负责把 agent 配置、任务内容、tool schema 和 policy 交给它。

2.2 每层职责

层职责不做什么
1 EntryWeb UI、REST API、认证、SSE / 事件推送不跑任务、不碰模型
2 Control任务定义与启停、cron 调度、手动触发、run 状态机、运行历史查询不执行、不直接调模型
3 Executionrun worker、每次 run 一个容器、harness adapter（上下文组装 / 工具循环）、agent 组装（model / tool / policy）、沙箱策略不定义任务、不管认证
4 Configagent、model / provider、tool（MCP / skill / agent）、policy、凭据引用不参与运行时决策
5 Control Planetrace、usage、audit、eval不进入业务判断链，只横切

2.3 依赖方向

  • 只能向下：Entry → Control → Execution → Config。
  • Control Plane 横切：Control 和 Execution 向它写事件与 span。
  • 只有 Execution/harness-adapter 允许 import 外部 harness SDK。
  • Config 只被读，不 import 运行时组件。
  • 存储、队列、密钥、日志是基础设施，不是架构层。
  • 反向依赖在 CI 直接失败。

2.4 为什么是五层

层数判断
三层（Entry / Control / Execution）缺配置与治理：凭据、policy、trace、eval 无处安放
五层（本方案）每层可独立替换：换 UI、换容器 / harness、换配置格式、换 eval 口径；控制平面不污染执行
六层以上（把 model gateway / tool 注入 / 存储单列）过度分层：它们是 Execution 的内部插件或基础设施，不是架构层

2.5 层 × 组件矩阵

层组件职责
EntryWebUI · API · Auth浏览器、REST、认证、SSE
ControlTaskRegistry · Scheduler · RunManager任务、cron、触发、run 状态
ExecutionRunWorker · Container · HarnessAdapter · AgentBuilder执行一次 run
ConfigConfigStoreagent / model / tool / policy 的读取与校验
Control PlaneTrace · Usage · Audit · Eval横切记录与评测

3 核心组件

3.1 九个核心组件

C7AgentBuilder把 agent 配置组装成 harness 输入（model / tools / policy）不执行 loop
C8ConfigStoreagent / model / tool / policy 的读写与校验不参与运行时决策
C9ControlPlanetrace、usage、audit、eval不进入业务判断链

3.2 组件边界

C1 Entry
唯一的产品入口
  • 输入：HTTP / 浏览器
  • 输出：API 响应 / SSE
  • 依赖：C2 / C4 / C9
  • 不依赖：C5 / C6
C2 TaskRegistry
任务定义的所有者
  • 输入：task CRUD / 启停
  • 输出：task 定义
  • 依赖：C8
  • 不依赖：C3 / C5
C3 Scheduler
时间的所有者
  • 输入：cron / 手动触发
  • 输出：trigger 事件
  • 依赖：C2 / C4
  • 不依赖：C6
C4 RunManager
run 状态与历史
  • 输入：trigger / run 事件
  • 输出：run 状态 / 历史
  • 依赖：C5 / C8 / C9
  • 不依赖：C6
C5 RunWorker
一次 run 的执行者
  • 输入：run 请求
  • 输出：事件 / 结果
  • 依赖：C6 / C7 / C9
  • 不依赖：C2 / C3
C6 HarnessAdapter
harness 的唯一边界
  • 输入：agent bundle + task
  • 输出：loop 事件 / 结果
  • 依赖：外部 harness SDK
  • 不依赖：C1–C5
C7 AgentBuilder
把配置组装成 harness 输入
  • 输入：agent id
  • 输出：model + tools + policy
  • 依赖：C8
  • 不依赖：C5
C8 ConfigStore
配置的事实源
  • 输入：agent / model / tool / policy
  • 输出：校验后的配置
  • 依赖：存储
  • 不依赖：运行时组件
C9 ControlPlane
观测与治理
  • 输入：span / usage / audit event
  • 输出：trace / usage / audit / eval
  • 依赖：存储 / OTel
  • 不依赖：业务状态

3.4 组件规则

  • 一个组件一个所有者：每类状态只有一个组件写。
  • 组件不互相 import：只经窄 API 或事件交互。
  • 组件可替换：C1 换 UI、C5 换容器运行时、C6 换 harness、C8 换存储。
  • harness 只在 C6 出现：任何其他组件不得 import 外部 harness SDK。
  • 新增能力是组件或插件：不改 C5 / C6 的 loop 语义。

4 几个窄 API

4.1 窄 API 原则

原则含义
一个面一个所有者每个组件只暴露一个 API 面，不提供 doEverything
按面计数本文的“8 个”指 8 个面；按方法数是 18 个，两者不矛盾
JSON Schema 跨边界不传内部类型；跨组件只传可序列化结构
additive-only加字段不改语义；破坏性变更走 major
错误是返回值typed code + retryable，不靠异常控制流
可替换API 稳定，实现可变

4.2 八个窄 API

#API方法谁调
A1TaskAPI（C2）create / update / setEnabled / listEntry
A2ScheduleAPI（C3）set / clearTaskRegistry
A3RunAPI（C4）start / get / list / cancelEntry / Scheduler
A4WorkerAPI（C5）executeRunManager
A5HarnessAPI（C6）runRunWorker

A7ConfigAPI（C8）get / put / validateTaskRegistry / AgentBuilder

4.3 API 详解

A1 TaskAPI — 任务定义

任务定义与启停的唯一入口。不负责调度，也不负责执行。

create(task) → taskId
update(taskId, patch) → Task
setEnabled(taskId, bool) → void
list(query) → Task[]

A2 ScheduleAPI — 调度

把任务的时间信息变成定时器；只管理 schedule，不创建 run。

set(taskId, cron) → void
clear(taskId) → void

A3 RunAPI — run 生命周期

run 状态机的唯一写入口；cron 到点和手动触发都走 start。

start(taskId, reason) → runId
get(runId) → Run
list(query) → Run[]
cancel(runId) → void

A4 WorkerAPI — 执行

在一个容器里执行一次 run；容器生命周期归它，agent 语义不归它。

execute(runId) → RunResult

A5 HarnessAPI — harness 边界

唯一允许 import 外部 harness 的地方；返回事件流，不解释事件语义。

run(bundle, input) → AsyncIterable<Event>

A6 AgentAPI — 组装

把 agent id 解析成 harness 可用的 bundle：model + tools + policy。

build(agentId) → HarnessBundle

A7 ConfigAPI — 配置

agent / model / tool / policy 的读写；只做校验，不做运行时决策。

get(kind, id) → Config
put(kind, id, config) → void
validate(config) → Result

A8 ControlAPI — 记录

所有组件的只写出口；trace / usage / audit / eval 都在这一面后面。

record(event) → void
query(q) → Result

4.4 八个 API 怎么拼成一次 run

sequenceDiagram participant S as C3 Scheduler participant E as C1 Entry participant R as C4 RunManager participant W as C5 RunWorker participant A as C7 AgentBuilder participant C as C8 ConfigStore participant H as C6 HarnessAdapter participant P as C9 ControlPlane S->>R: A3.start(taskId, "cron") E->>R: A3.start(taskId, "manual") R->>R: 创建 run R->>W: A4.execute(runId) W->>A: A6.build(agentId) A->>C: A7.get(agent / model / tool / policy) C-->>A: config A-->>W: HarnessBundle W->>H: A5.run(bundle, input) loop 每个事件 H-->>W: Event W->>P: A8.record(event) end H-->>W: RunResult W-->>R: RunResult R->>P: A8.record(run finished) R-->>E: SSE 状态更新

4.5 为什么是这 8 个

  • 对应 8 个内部组件（C2–C9），一个组件一个面。
  • C1 Entry 不算：它对外暴露 REST / SSE，不是内部窄 API。
  • 每个面只做一件事；复合流程由调用方组合。
  • 8 个面、18 个方法；按面数说 8，按方法数说 18。
  • 新增能力 = 新组件或新实现，不加面。
